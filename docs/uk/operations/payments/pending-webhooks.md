# Очікувані вебхуки

Сторінка Очікувані вебхуки (`/payments/pending-webhooks`) показує платіжні транзакції, які застрягли в статусі **Очікується**, оскільки підтвердження вебхука від платіжного провайдера ще не надійшло.

Кожен рядок — це платіж, який ми надіслали провайдеру, але не отримали остаточного зворотного виклику зі статусом. Використовуйте цю сторінку як ваш **чергу застряглих платежів**: перевіряйте старі рядки, визначайте провайдера, який відстає, і ескалюйте.

Потрібен дозвіл: **Платежі** (`m1n2p3`).

## Що ви бачите

Коли клієнт платить:

1. Панель керування надсилає запит на платіж до **провайдера** (Stripe, шлюз тощо) — створюється _Payment Intent_
2. Провайдер асинхронно обробляє транзакцію і надсилає **вебхук** з остаточним статусом (`succeeded`, `failed` тощо)
3. Панель керування отримує вебхук і змінює статус [платежу](payments.md) з _Очікується_ на _Завершено_ / _Помилка_

Рядки в **Очікуваних вебхуках** — це крок 2, що завис: провайдера було оповіщено, але він не надіслав відповідь. Зазвичай вебхук надходить за секунди, іноді за хвилини. Все, що старше ~30 хвилин, викликає підозру; все, що старше 2 годин, майже напевно зламано на боці провайдера або в нашому приймачі вебхуків.

## Фільтри

| Фільтр          | Тип     | Примітки                                                                            |
| --------------- | ------- | ----------------------------------------------------------------------------------- |
| **Провайдер**   | Текст   | Пошук за назвою провайдера (наприклад, `stripe`)                                   |
| **Старше ніж**  | Вибір   | `Всі` / `5` / `15` / `30` / `60` / `120` хвилин — показувати лише рядки старші за це |

Використовуйте _Старше ніж 30 хв_ або _60 хв_ як щоденний фільтр моніторингу — свіжі очікувані — це шум.

## Колонки

| Колонка               | Сортується? | Зміст                                                                                 |
| --------------------- | ---------- | ------------------------------------------------------------------------------------- |
| **Створено**          | ✓          | Коли було створено платіжний намір                                                    |
| **Вік**               | ✓          | Хвилин з моменту створення — кольорове кодування (див. нижче)                         |
| **Провайдер**         | —          | Провайдер платежу, якому надіслано намір                                            |
| **ID платіжного наміру** | —          | ID провайдера для цього наміру — копіюйте при ескалації                              |
| **Статус**            | —          | Статус на боці провайдера (сирий) — зазвичай `requires_action` / `processing`        |
| **ID замовлення**     | —          | Наш внутрішній ID замовлення/платежу                                                |

### Кольорове кодування віку

Колонка **Вік** змінює колір із збільшенням часу, щоб ви могли швидко оцінити ситуацію:

| Вік             | Колір  | Що робити                                      |
| --------------- | ------ | ---------------------------------------------- |
| **< 30 хв**     | Сірий  | Нормально; ігноруйте                          |
| **30–120 хв**   | Жовтий | Варто переглянути; перевірте панель провайдера |
| **> 120 хв**    | Червоний | Майже напевно зламано — ескалюйте              |

## Дії з рядком

Невелике меню дій праворуч від кожного рядка:

| Дія              | Що робить                                               |
| ---------------- | ------------------------------------------------------- |
| **Переглянути клієнта** | Відкрити профіль клієнта, пов’язаний із цим платіжним наміром |

(Дія _Переглянути деталі платежу_ є в коді, але тимчасово відключена, оскільки сторінка деталей платежу вилучена — повернеться пізніше.)

## Типові робочі процеси

- **Щоденний моніторинг** — встановіть _Старше ніж = 30 хв_ → сторінка має бути порожньою більшість часу → якщо ні, перевірте колонку провайдера
- **Відмова одного провайдера** — бачите багато рядків одного провайдера, що одночасно жовтіють/червоніють → перевірте сторінку статусу провайдера → зверніться до їхньої підтримки з кількома _ID платіжних намірів_ із таблиці
- **Проблема одного клієнта** — один-два старі рядки → _Переглянути клієнта_ → перевірте [Активність / Платежі](../customers/client-detail.md) клієнта → скажіть їм повторити спробу або використати інший метод
- **Проблема приймача вебхуків** — багато провайдерів одночасно червоніють без відмови на боці провайдера → проблема в нашому приймачі вебхуків, а не в провайдері; ескалюйте до інженерної команди

## Коли рядок зникає

Рядок зникає зі сторінки, коли надходить вебхук — статус платежу змінюється на _Завершено_ або _Помилка_ у головному [списку платежів](payments.md). Рядок ніколи не "старіє" сам по собі; лише вебхук його очищує.

Якщо у вас є **застряглі очікувані платежі старші за день**, які не зникають, це баг для ескалації — у панелі оператора немає кнопки "примусово завершити" з міркувань безпеки (неправильне ручне завершення створює бухгалтерський безлад, який важко виправити).

## Поради

- **Копіюйте ID платіжного наміру** при ескалації до провайдера — це єдиний ID, який вони розпізнають
- **Сортування за віком** (спочатку новіші → потім старіші) дає вам чергу для сортування: верх списку — ваша термінова робота
- **Порожня сторінка — це мета** — Очікувані вебхуки мають бути порожніми (або майже порожніми) у звичайний день; будь-які рядки — це робота
- **Пошук провайдера гнучкий** — працюють часткові збіги (`stri` збігається з `stripe`)
- **Сторінка не оновлюється автоматично** — використовуйте кнопку оновлення або перезавантажуйте сторінку під час активного сортування
