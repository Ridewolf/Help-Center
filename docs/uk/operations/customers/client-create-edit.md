# Клієнт — Створення та редагування

Два URL-адреси:

- **Створити** — `/clients/create` — вручну зареєструвати нового клієнта (рідко; більшість клієнтів реєструються самостійно)
- **Редагувати** — `/clients/:id/edit` — оновити особисті дані та статус існуючого клієнта

Обидва доступні зі списку [Клієнтів](clients.md) (кнопка `+ Створити` у верхньому правому куті) або зі сторінки [Деталі клієнта](client-detail.md) (_Дії → Редагувати клієнта_).

Дозволи:

- **Створити** — `Clients` (`e4f5h6`) + піддозвіл на створення
- **Редагувати** — `Clients` (`e4f5h6`) + піддозвіл `edit`

## Коли використовувати

Більшість ваших клієнтів **реєструються самостійно** через мобільний додаток Rider App — ви рідко створюєте їх у Панелі керування.

Ручне створення призначене для:

- **Тестових акаунтів** — внутрішнє тестування, демонстраційні користувачі
- **VIP / корпоративних** — акаунти, які мають існувати до завантаження додатка користувачем
- **Онбордингу, керованого оператором** — події / партнерства, де співробітники реєструють користувача від його імені

Для всього іншого дозвольте додатку обробляти реєстрацію, а **Редагування** використовуйте для виправлення контактної інформації або зміни статусу.

## Макет

Одна картка з вертикальною формою, без бокової панелі Field Guide (на відміну від форми Транспортного засобу).

## Поля — Створення

Всього сім полів. Всі обов’язкові.

| Поле                | Валідація                                                                                                             |
| -------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Ім'я**             | 1–100 символів                                                                                                         |
| **Прізвище**         | 1–100 символів                                                                                                         |
| **Електронна пошта** | Стандартний формат email (`name@domain.tld`); має бути унікальним серед клієнтів                                        |
| **Телефон**          | Міжнародний формат, починається з `+` (наприклад, `+373 60 123 456`); лише цифри, пробіли, дефіси, дужки               |
| **Пароль**           | **Щонайменше 12 символів**, має містити **велику літеру, малу літеру, цифру та спеціальний символ**                     |
| **Підтвердження пароля** | Має точно співпадати з паролем                                                                                        |
| **Статус**           | Початковий статус: `Активний` / `Неактивний` / `Заблоковано` / `Заморожено` / `Реєстрація` (за замовчуванням _Активний_) |

Валідація виконується при збереженні та під час виходу з поля. Помилки відображаються червоним під полем.

### Правила пароля

Вимоги до пароля найсуворіші. Панель керування відхиляє будь-який пароль, що не відповідає всім чотирьом перевіркам:

- ≥ 12 символів
- ≥ 1 велика літера (A–Z)
- ≥ 1 мала літера (a–z)
- ≥ 1 цифра (0–9)
- ≥ 1 спеціальний символ (наприклад, `!@#$%^&*`)

Після збереження клієнт використовуватиме цей пароль (разом із телефоном або електронною поштою) для входу в мобільний додаток Rider App. Повідомляйте пароль через перевірений канал — ніколи не вставляйте паролі у чати без наскрізного шифрування.

### Статус (при створенні)

| Значення        | Використання                                                                                  |
| --------------- | -------------------------------------------------------------------------------------------- |
| **Активний**    | За замовчуванням — клієнт може одразу користуватися послугами                                |
| **Неактивний**  | Створений, але ще не активований (пізніше можна переключити на Активний)                     |
| **Заблоковано** | Попередньо заблокований (рідко — зазвичай при відновленні акаунта після шахрайства)          |
| **Заморожено**  | Акаунт призупинено                                                                           |
| **Реєстрація**  | Реєстрація ще триває (використовується лише при інтеграції з зовнішнім потоком)              |

## Поля — Редагування

У режимі редагування поля пароля приховані (їх скидають в іншому місці) і додається поле **Теги**.

| Поле          | Примітки                                                                                 |
| -------------- | --------------------------------------------------------------------------------------- |
| **Ім'я**       | Заповнене заздалегідь, та сама валідація, що й при створенні                            |
| **Прізвище**   | Заповнене заздалегідь, та сама валідація, що й при створенні                            |
| **Електронна пошта** | Заповнене заздалегідь; зміна може порушити вхід клієнта, доки він не підтвердить нову пошту |
| **Телефон**    | Заповнене заздалегідь; те саме застереження, що й для електронної пошти                 |
| **Теги**       | Мультивибір; мітки, які оператор додає для групування та фільтрації                    |
| **Статус**     | Заповнене заздалегідь поточним статусом; той самий перелік                              |

## Зберегти / Скасувати

- **Скасувати** (або стрілка назад) — відкидає незбережені зміни і повертає на попередню сторінку
- **Зберегти** — перевіряє форму і створює / оновлює клієнта. Підтвердження у вигляді тосту; помилки підсвічуються червоним на рівні полів

Якщо валідація не проходить (відсутнє поле, порушення правил пароля, дубль email, формат телефону), сторінка залишається відкритою, а проблемне поле обведене.

## Відмінності між Створенням і Редагуванням

| Аспект            | Створення                                              | Редагування                                          |
| ------------------ | ------------------------------------------------------- | ---------------------------------------------------- |
| Поля пароля       | Присутні та обов’язкові                                | Приховані                                            |
| Теги              | Відсутні у формі (встановлюються пізніше через Редагування або список/деталі) | Присутні                                             |
| Статус            | Порожній → за замовчуванням _Активний_                 | Заповнений поточним статусом                         |
| Email / Телефон   | Порожні                                                 | Заповнені — зміна може вимагати повторної верифікації |
| Після збереження  | Перенаправлення на деталі нового клієнта                | Перенаправлення назад до деталей клієнта            |
| Запис у журналі дій | "Клієнт створений _ім'я оператора_"                   | "Клієнт відредагований _ім'я оператора_" з відмінностями полів |


Обидва процеси записують у [Журнал дій](client-detail.md#вкладка-активність) клієнта.

## Типові робочі процеси

- **Створити VIP** — `+ Створити` у списку → заповнити ім'я, реальний email, реальний телефон, надійний пароль, статус _Активний_ → зберегти → повідомити користувача з обліковими даними
- **Виправити помилку** — рядок списку → меню рядка → _Редагувати_ → виправити поле → зберегти (зміна відображається в Журналі з відмінностями)
- **Реєстрація корпоративної партії** — створення через API (ця форма для одиничних записів); пізніше використовуйте Редагування для застосування тегів компанії
- **Змінити телефон після заміни пристрою** — Редагувати → оновити Телефон → зберегти → клієнту потрібно буде повторно пройти верифікацію при наступному вході (залежно від правил бекенда)

## Поради

- **Формат телефону має значення** — повинен починатися з `+` та коду країни; формат контролюється, валідатор відхилить некоректний ввід
- **Вибір надійного пароля** — для одиничного створення оператором використовуйте довгу фразу ("rideTheWolf2026!RW"), що одночасно задовольняє всі правила; збережіть її у менеджері паролів, а не в чаті
- **Унікальність email** — дублікати email найчастіша причина помилки при створенні; спочатку перевірте список за email
- **Не змінюйте Email / Телефон без потреби у існуючих клієнтів** — від них залежить верифікація; узгоджуйте зі клієнтом перед збереженням
- **Теги належать сюди, а не в рядок** — також можна додавати/видаляти теги через масові дії у списку, але форма редагування — правильне місце для точкових змін
- **Зміни статусу мають вагу аудиту** — перехід _Активний → Заблоковано_ через цю форму фіксується так само, як і через спеціальну дію _Дії → Заблокувати клієнта_ — обидва варіанти дійсні
