# Тикеты — Список

Список тикетов (`/support/tickets`) — это support-очередь по проблемам с транспортом: механические повреждения, электрические неисправности, сломанные части, проблемы безопасности и т.п. Каждый тикет привязан к конкретному транспорту и содержит фото, репортёра, тип жалобы, SLA-таймер и статус.

Для разбора одного тикета (полная переписка, evidence, действия) см. **страницу детали** (открывается кликом по строке).

Для streamlined-очереди см. [Ticket Auto Review](ticket-auto-review.md).

Требуется право: **Tickets** (`a8b9c1`).

## Откуда тут тикеты

Тикеты создаются из нескольких источников:

1. **Жалоба райдера** — в мобильном приложении есть flow "пожаловаться на проблему"; райдер выбирает тип, делает фото, пишет заметку
2. **Operator-initiated** — оператор открывает тикет на транспорт, в котором заметил проблему (редко; обычно используется [maintenance task](../../operations/fleet/vehicle-detail.md))
3. **System-flagged** — IoT или analytics могут поднимать тикеты автоматически (например, аномалия батареи)

Каждый новый тикет попадает в список со статусом (обычно _Pending_) и стартует SLA-таймер.

## Типы жалоб

Семь типов помогают сортировать тикеты на лету. Каждый окрашен:

| Тип                   | Цвет бейджа           | Что обычно значит                                         |
| --------------------- | --------------------- | --------------------------------------------------------- |
| **Mechanical damage** | Destructive (красный) | Авария, сломанная рама, погнутые компоненты               |
| **Electrical issue**  | Warning (жёлтый)      | Газ, фары, проблемы датчиков                              |
| **Battery problem**   | Default (синий)       | Не заряжается, разряжается быстрее чем должна             |
| **Broken parts**      | Destructive (красный) | Нет подножки, отсутствует рефлектор, повреждённые тормоза |
| **Safety concern**    | Destructive (красный) | Всё что делает транспорт небезопасным                     |
| **Cleanliness**       | Warning (жёлтый)      | Грязный, запах, липкие поверхности — менее срочно         |
| **Other**             | Outline               | Не попадает в категории выше — читайте описание           |

Красные категории обычно требуют немедленного вывода из эксплуатации; жёлтые/синие могут подождать service-окна.

## Справка по статусам

Список статусов приходит с бека, поэтому может слегка отличаться по deployment. Типичные:

| Статус          | Variant               | Значение                                              |
| --------------- | --------------------- | ----------------------------------------------------- |
| **Pending**     | Secondary (серый)     | Только что зарепортили, никто не работает             |
| **In progress** | Default (синий)       | Назначен оператору или создан maintenance-task        |
| **Resolved**    | Success (зелёный)     | Проблема решена; тикет закрыт                         |
| **Rejected**    | Destructive (красный) | Оператор решил что это не реальная проблема           |
| **Cancelled**   | Destructive (красный) | Закрыт без resolution (часто для low-quality reports) |
| **Archived**    | Outline               | Старый / исторический                                 |
| **Duplicate**   | (закрыт)              | Связан с более ранним тикетом на том же транспорте    |

Статусы содержащие _resolved_, _dismissed_ или _duplicate_ считаются **закрытыми** — не учитываются в открытой очереди.

## Severity

Внутри тикет несёт severity (`critical`, `high`, `medium`, `low`), выведенный из типа жалобы и оператор/system input. На списке severity видна через **цвет complaint-type** и **цвет SLA-таймера** — просроченная SLA на critical-тикете = ваш топ-приоритет.

## Действия над строкой

У каждой строки **меню из трёх точек** с одним активным пунктом:

| Действие         | Что делает                                                                 |
| ---------------- | -------------------------------------------------------------------------- |
| **View details** | Открыть детальную страницу тикета (полная переписка + evidence + действия) |

Полный набор действий оператора (Assign, Block vehicle, Create maintenance task, Credit user, Reply, Merge duplicate) живёт на **детальной странице** и feature-flag'нут по deployment. Задача списка — быть очередью триажа, не resolution-консолью.

## Действия страницы

- **Auto Review** — открывает [очередь Ticket Auto Review](ticket-auto-review.md) — streamlined по одному тикету за раз

## Типичные сценарии

- **Дневной триаж** — `Status = Pending` → сорт по SLA (старые сверху, ближайший дедлайн сверху) → пройти каждый, открыть в деталь, решить и действовать
- **Только critical** — `Complaint type = Mechanical damage / Safety concern` → это take-out-of-service тикеты
- **История транспорта** — поиск по метке транспорта → каждый тикет на эту единицу → полезно перед выпуском после ремонта
- **SLA-алерт** — сорт по SLA → топ списка = overdue → эскалируйте немедленно

## Полезные приёмы

- **Фото — ваш первый сигнал** — даже до открытия миниатюра говорит реальное ли это damage или low-quality report
- **Красная SLA = действовать сейчас** — к моменту когда SLA краснеет, contractual окно уже пропущено; это реактивная очередь
- **Сверяйтесь с транспортом** — клик по колонке Vehicle → откройте таб Alerts → IoT-проблемы и operator-репорты часто пересекаются
- **Следите за дубликатами** — несколько райдеров часто репортят один сломанный самокат в течение часов; используйте поиск по транспорту чтобы их найти до resolution
- **URL шарится** — копируйте отфильтрованный вид (например, _pending mechanical-damage_) и отправляйте maintenance-команде
