# Аналитика — Recent Events

Страница событий (`/analytics/events`) — это ваш **incident-дашборд**: каждое заметное system / vehicle / user / zone событие за период с KPI-счётчиками, паттернами по времени и searchable feed внизу.

В отличие от [панели уведомлений](../../features/ux/notifications.md) (real-time, per-event), эта страница **агрегирована и историческая** — для трендов и post-incident review.

Требуется право: **View Recent Events** (`s1t2u3`).

## Период и фильтры

Сверху **date-range bar** — все метрики и графики используют его. Четыре доп. фильтра сужают вид:

| Фильтр          | Опции                                                                   |
| --------------- | ----------------------------------------------------------------------- |
| **Severity**    | `critical` / `warning` / `info` (multi-select)                          |
| **Type**        | `error` / `offline` / `battery` / `payment` / `support` / `maintenance` |
| **Source type** | `vehicle` / `user` / `zone` / `system`                                  |
| **Status**      | `open` / `resolved` / `dismissed`                                       |

Все фильтры И-комбинируются. URL отражает каждую настройку — поделитесь ссылкой, коллега увидит ту же выборку.

## Секции

Страница содержит **пять секций**:

### 1. Summary

Четыре карточки суммаризуют счётчики:

| KPI          | Что показывает                                                  |
| ------------ | --------------------------------------------------------------- |
| **Total**    | Общее число событий за период                                   |
| **Critical** | Счёт с `severity = critical` — обязательное число для просмотра |
| **Warning**  | Счёт с `severity = warning`                                     |
| **Info**     | Счёт с `severity = info` — обычно шум, если не всплеск          |

У каждой карточки — comparison-бейдж "vs предыдущий период".

### 2. By Type

График разбивки событий по **типу**:

- **Error** — system / integration failures
- **Offline** — IoT-устройства уходят в офлайн
- **Battery** — low / depleted / anomaly alarms
- **Payment** — declines, gateway issues
- **Support** — ticket / chat всплески
- **Maintenance** — service-related события

Всплеск в одном типе — обычно стартовая точка расследования.

### 3. Patterns

Два time-series графика:

- **By Day** — события в день по периоду (видны недельные циклы)
- **By Hour** — события в час дня по периоду (видны дневные пики)

### 4. Top Sources

Список **топ-источников** генерирующих события — обычно отдельные транспорты или зоны с непропорционально многими событиями.

Каждая запись: source (ссылка на детальную), счёт событий, доминирующая severity / type.

Здесь находите **транспорт который алармит всю неделю** или **зону с battery-проблемами**.

### 5. Feed

Скроллируемый feed индивидуальных событий по текущим фильтрам. Каждая строка:

- Severity-иконка (цветная)
- Event type + source label
- Краткое описание
- Timestamp
- Status pill

Клик по элементу feed открывает связанную сущность (vehicle, client, ride, ticket) где применимо.

## Типичные сценарии

- **Утренний обзор** — preset _Last 24h_ → Severity = Critical → сканировать; всё красное в приоритете до открытия остального
- **Top sources триаж** — секция Top sources → клик по транспорту который постоянно появляется → исправить или эскалировать в источнике
- **Pattern detection** — patterns-графики; необычный день или час = что-то изменилось (deploy, погода, outage)
- **Post-incident review** — выбрать день → severity = critical → сверка Feed с табом Alerts [транспорта](../../operations/fleet/vehicle-detail.md) или Quality-секцией [Payments analytics](payments.md) в зависимости от типа
- **Cleanup pass** — Status = Open → bulk-resolve залежавшихся (делается из source-страниц, не отсюда; но находите их здесь)

## Полезные приёмы

- **Critical первым** — начните с `severity = critical`; warnings и info часто разрешаются сами
- **Type — ваш детектив** — всплеск + фильтр по доминирующему типу = шум сужается
- **Top sources — золото** — один транспорт сверху списка обычно объясняет 30-50% всех событий
- **Aggregations vs raw** — эта страница агрегирует; для конкретных транзакций / алертов идите на доменную страницу
- **Sticky фильтры** — настройки переживают навигацию; очищайте перед отправкой URL коллеге
- **Status `open` ≠ нерешённый IoT-аларм** — Status здесь это статус _event record_; underlying alarm может быть очищен на устройстве пока event всё ещё open в системе
