# Платежи — История

Страница Платежи (`/payments`) — это бухгалтерская книга каждой денежной транзакции, затронувшей аккаунт клиента: списания за поездки, пополнения кошелька, возвраты, штрафы. Используйте чтобы разобрать списание, выдать возврат или аудитировать денежный поток за период.

Для необработанных webhook-событий от платёжных провайдеров см. [Pending Webhooks](pending-webhooks.md).

Требуется право: **Payments** (`m1n2p3`). Некоторые row actions требуют доп. под-прав.

## Что здесь живёт

Каждая строка — это одна платёжная транзакция:

| Тип        | Что это                                                                         |
| ---------- | ------------------------------------------------------------------------------- |
| **Topup**  | Деньги добавлены на кошелёк клиента (ручной operator-кредит или top-up с карты) |
| **Debit**  | Деньги списаны с клиента (заряд за поездку или штраф)                           |
| **Refund** | Деньги возвращены клиенту (реверс предыдущего debit)                            |

У каждой транзакции есть **метод/провайдер** — канал по которому она прошла:

- **Card-провайдеры** (Stripe и пр.) — настоящие деньги на платёжной карте
- **Balance** — внутренний кошелёк (не платёжный провайдер; просто debit/credit на баланс клиента)
- **Другие шлюзы** в зависимости от интеграций

Разделение между _card provider_ и _balance_ важно для возврата — см. _Действия над строкой → Refund_ ниже.

## Фильтры

| Фильтр     | Тип       | Заметки                                                     |
| ---------- | --------- | ----------------------------------------------------------- |
| Search     | Текст     | Ищет по имени клиента, ID платежа, связанному ride/fine ID  |
| Date range | Календарь | От / до; по умолчанию "за всё время"                        |
| Type       | Дропдаун  | `Topup` / `Debit` / `Refund` (или `All`)                    |
| Status     | Дропдаун  | `Pending` / `Completed` / `Failed` / `Refunded` (или `All`) |

Фильтры применяются server-side и И-комбинируются.

## Колонки

| Колонка    | Сортировка? | Содержимое                                                 |
| ---------- | ----------- | ---------------------------------------------------------- |
| **Date**   | ✓           | Когда транзакция создана; по умолчанию сорт = новые сверху |
| **Client** | —           | Имя клиента и аватар; ссылка на деталь                     |
| **Source** | —           | Тип транзакции (Topup / Debit / Refund), с цветным тегом   |
| **Amount** | ✓           | Сумма в валюте компании, со знаком (+/−) и цветом          |
| **Method** | —           | Способ оплаты / провайдер (card, balance, имя шлюза)       |
| **Status** | ✓           | Пилюля статуса (справка ниже)                              |

Сортировка кликом по заголовку. Сорт попадает в URL.

## Справка по статусам

| Статус        | Значение                                                          |
| ------------- | ----------------------------------------------------------------- |
| **Pending**   | Отправлено провайдеру; ждём webhook-подтверждение                 |
| **Completed** | Провайдер подтвердил успех; деньги перемещены                     |
| **Failed**    | Провайдер отказал (decline карты, сетевая ошибка, fraud-проверка) |
| **Refunded**  | Успешный debit, который позже реверсирован возвратом              |

## Действия над строкой

У каждой строки справа — **меню из трёх точек**. Доступные действия зависят от типа платежа, статуса и ваших прав:

| Действие        | Когда активно                       | Право                                                    |
| --------------- | ----------------------------------- | -------------------------------------------------------- |
| **View client** | Всегда (переход на профиль клиента) | —                                                        |
| **Refund**      | См. "Маршрутизация возврата" ниже   | `refund` / `topup-manual` / `fine` (зависит от маршрута) |

### Маршрутизация возврата

Дашборд прячет от вас детали провайдера, но _Refund_ умный — он сам выбирает правильный путь:

- **Provider-based debit** (карта, шлюз) → вызов refund endpoint провайдера → деньги возвращаются на карту
- **Balance debit** (кошелёк) → провайдера нет — открывается диалог **Top up balance** для кредитования кошелька (требуется `topup-manual`)
- **Balance top-up** (ручной operator-кредит) → нельзя реверсировать через провайдера — открывается диалог **Issue fine** для дебета той же суммы (требуется `fine`)

Refund **отключён** когда:

- Строка сама refund (возврат возврата не имеет смысла)
- Статус не _Completed_ (нельзя вернуть pending / failed)
- Транзакция уже реверсирована (дашборд отслеживает это и блокирует дубликаты кликов)
- У вас нет нужного под-права для маршрута

## Откуда здесь платежи (и что их создаёт)

Платежи **не** создаются с этой страницы — они приходят из других flow:

1. **Райдер делает поездку** → конец поездки → бэк создаёт _Debit_-транзакцию → если успешна, статус _Completed_ и деньги списаны с кошелька или карты
2. **Райдер пополняет кошелёк в приложении** → вызов провайдера → бэк создаёт _Topup_ → статус _Completed_ по webhook
3. **Оператор пополняет кошелёк** через _Top up balance_ на клиенте → бэк создаёт _Topup_ с methodom _balance_, сразу _Completed_
4. **Оператор выдаёт штраф** → бэк создаёт _Debit_ с methodom _balance_, сразу _Completed_
5. **Refund** из этого списка → бэк создаёт _Refund_-транзакцию; оригинал помечается _Refunded_

Оригинальная транзакция никогда не исчезает — каждое действие аудитируемо.

## Типичные сценарии

- **Расследовать списание** — поиск по клиенту / поездке / ID платежа → проверьте Status (Completed = деньги взяты, Failed = нет) и Method
- **Возврат за поездку** — найти строку _Debit_ для поездки → меню → _Refund_ → подтвердить → появится парная _Refund_-строка, оригинал станет _Refunded_
- **Аудит дня** — Date range = сегодня → Status = Completed → проверить totals
- **Найти failures для retry** — Status = Failed → связаться с клиентами для повторной попытки / альтернативного метода
- **Сверка с провайдером** — Date range + Type = Topup/Debit + Method = card → экспорт и сверка с выпиской провайдера

## Полезные приёмы

- **Pending — это не failed** — pending ждёт webhook провайдера; проверьте [Pending Webhooks](pending-webhooks.md) если строка зависла в Pending
- **Balance-транзакции нельзя card-вернуть** — система маршрутизирует в правильный диалог; не пытайтесь вручную создавать offset-транзакции
- **Оригинал переживает refund** — возврат добавляет парную строку, не удаляет debit; обе строки в истории для аудита
- **Знак суммы говорит направление** — `+` (зелёный) = деньги клиенту; `−` (красный/тёмный) = деньги с клиента
- **Имена провайдеров важны для саппорта** — при эскалации к провайдеру скопируйте payment ID и имя провайдера из Method
- **URL шарится** — копируйте отфильтрованный вид (например, _вчерашние failed card debits_) и отправляйте финансам или fraud
