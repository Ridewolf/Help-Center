# Pending Webhooks

Страница Pending Webhooks (`/payments/pending-webhooks`) показывает платёжные транзакции, застрявшие в **Pending**, потому что webhook-подтверждение от провайдера ещё не пришло.

Каждая строка — это платёж, который мы отправили провайдеру, но финальный коллбэк со статусом так и не получили. Используйте страницу как **очередь застрявших платежей**: ищите старые строки, определяйте провайдера который тормозит, эскалируйте.

Требуется право: **Payments** (`m1n2p3`).

## Что вы видите

Когда клиент платит:

1. Дашборд отправляет платёжный запрос **провайдеру** (Stripe, шлюз и т.д.) — создаётся _Payment Intent_
2. Провайдер обрабатывает асинхронно и присылает **webhook** с финальным статусом (`succeeded`, `failed` и т.д.)
3. Дашборд слышит webhook и переключает статус [платежа](payments.md) с _Pending_ на _Completed_ / _Failed_

Строки на **Pending Webhooks** — это шаг 2 зависший — провайдер был связан, но не отчитался. Чаще всего webhook приходит за секунды, иногда минуты. Что-то старше ~30 минут подозрительно; старше 2 часов — почти наверняка сломано на стороне провайдера или нашего webhook-приёмника.

## Фильтры

| Фильтр         | Тип    | Заметки                                                        |
| -------------- | ------ | -------------------------------------------------------------- |
| **Provider**   | Текст  | Поиск по имени провайдера (например, `stripe`)                 |
| **Older than** | Select | `All` / `5` / `15` / `30` / `60` / `120` минут — только старше |

Используйте _Older than 30 min_ или _60 min_ как дневной фильтр мониторинга — свежие pending это шум.

## Колонки

| Колонка               | Сортировка? | Содержимое                                                                   |
| --------------------- | ----------- | ---------------------------------------------------------------------------- |
| **Created at**        | ✓           | Когда был создан payment intent                                              |
| **Age**               | ✓           | Минуты с создания — с цветовой кодировкой (ниже)                             |
| **Provider**          | —           | Платёжный провайдер, которому был отправлен intent                           |
| **Payment Intent ID** | —           | ID intent на стороне провайдера — копируйте при эскалации                    |
| **Status**            | —           | Статус на стороне провайдера (raw) — обычно `requires_action` / `processing` |
| **Order ID**          | —           | Наш внутренний order / payment ID                                            |

### Цветовая кодировка Age

Колонка **Age** меняет цвет с возрастом, чтобы вы могли сканировать и сортировать в один взгляд:

| Возраст        | Цвет    | Что делать                                  |
| -------------- | ------- | ------------------------------------------- |
| **< 30 мин**   | Серый   | Норма; игнорировать                         |
| **30–120 мин** | Жёлтый  | Стоит глянуть; проверьте дашборд провайдера |
| **> 120 мин**  | Красный | Почти наверняка сломано — эскалируйте       |

## Действия над строкой

Маленькое меню действий справа у каждой строки:

| Действие        | Что делает                                    |
| --------------- | --------------------------------------------- |
| **View client** | Открыть профиль клиента, привязанный к intent |

## Типичные сценарии

- **Дневной мониторинг** — _Older than = 30 min_ → страница должна быть пустой большую часть времени → если нет, сканируйте колонку Provider
- **Сбой одного провайдера** — много строк одного провайдера одновременно желтеют/краснеют → проверьте status-page провайдера → свяжитесь с их поддержкой с несколькими _Payment Intent IDs_ из таблицы
- **Проблема одного клиента** — одна-две старых строки → _View client_ → проверьте Activity / Payments клиента → попросите клиента повторить или использовать другой метод
- **Проблема webhook-приёмника** — много провайдеров краснеет одновременно без сбоя на их стороне → проблема в нашем webhook-приёмнике, эскалируйте инженерам

## Когда строка исчезает

Строка уходит со страницы когда webhook приходит — статус платежа переключается на _Completed_ или _Failed_ в основном [списке платежей](payments.md). Сама собой строка не "стареет" — только webhook её убирает.

Если у вас **застрявшие pending старше суток** не исчезают, это баг для эскалации — у operator-дашборда нет ручной кнопки "force complete" по соображениям безопасности (неверное ручное закрытие создаёт accounting-беспорядок который тяжело распутать).

## Полезные приёмы

- **Копируйте Payment Intent ID** при эскалации к провайдеру — это единственный ID, который они узнают
- **Сорт по Age** (от старых сверху) даёт очередь приоритизации: верх отсортированного списка — ваша срочная работа
- **Пустая страница — это цель** — Pending Webhooks должны быть пустыми (или почти) в нормальный день; любые строки = работа
- **Поиск провайдера loose** — частичные совпадения работают (`stri` находит `stripe`)
- **Страница не автообновляется** — используйте кнопку refresh или перезагрузите при активной триаже
