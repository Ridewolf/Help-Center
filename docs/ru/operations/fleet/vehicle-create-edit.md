# Транспорт — Создание и редактирование

Два URL с одинаковым layout-ом формы:

- **Создание** — `/vehicles/create` — регистрация новой физической единицы
- **Редактирование** — `/vehicles/:id/edit` — обновление метаданных существующего транспорта

К обоим попадают из [списка транспорта](vehicles.md) (кнопка `+ Создать` сверху-справа) или из [детали транспорта](vehicle-detail.md) (`Actions → Edit vehicle`).

Права:

- **Создание** — `Vehicles` (`k7m8n9`) + create-связанное под-право
- **Редактирование** — `Vehicles` (`k7m8n9`) + под-право `edit`

## Структура

Страница делится на две колонки на десктопе, складывается на мобильном:

- **Слева (8/12)** — сама форма внутри карточки _Vehicle information_
- **Справа (4/12)** — сайдбар **Field Guide** с контекстной подсказкой для текущего поля и live-превью введённых данных

## Поля

Всего пять полей. Обязательные помечены красной звёздочкой (`*`).

### 1. Label (обязательное)

Читаемый код, напечатанный на стикере транспорта (например, _RW-001_).

- Должен быть уникальным по всему флоту
- Свободный текст — типичная конвенция _PREFIX-NNN_ (префикс компании + порядковый номер)
- Кнопка **Generate** (иконка искры) автозаполняет — система читает префикс компании и существующие метки, вычисляет следующий номер и подставляет. Спиннер показан пока идёт запрос.

### 2. Status (обязательное)

Начальный / текущий статус транспорта. Двенадцать опций — тот же список что и в [фильтре списка](vehicles.md#справка-по-статусам).

Типичные стартовые значения при создании:

- **Not Ready** — создан, но ещё не выпущен к райдерам (дефолтный безопасный выбор)
- **Available** — готов к аренде сразу (используйте только после проверки IoT и парковки)
- **Storage** — для запасов которые не в эксплуатации пока

При редактировании меняйте статус осторожно — это может вывести транспорт из аренды или вернуть в неё.

### 3. IoT Device (опциональное)

IoT-модуль привязанный к транспорту (сотовая коробка отвечающая за lock/unlock и отчитывающаяся о батарее/GPS).

- Searchable дропдаун — набирайте чтобы фильтровать по IMEI или метке
- Опциональное — можно создать транспорт без IoT сейчас и привязать позже (в _Edit_)
- Один IoT может быть привязан только к одному транспорту в момент времени

При редактировании, замена IoT разрешена но похожа на необратимую — новое устройство начинает отчитываться под этим транспортом, старое отвязывается. Используйте при физической замене платы.

### 4. Vehicle Model (опциональное)

Запись модели (Настройки → Vehicle Settings) определяющая тарифы, дефолтные настройки и категорию единицы.

- Searchable дропдаун — набирайте чтобы фильтровать по метке модели
- Опциональное при создании, рекомендуется выставлять сразу как только знаете модель — тарифы и поведение приходят из неё
- Смена модели позже обновляет активные тарифы и правила поведения — подтверждайте с операциями перед сменой на live-единице

### 5. Tags (опциональное)

Оператор-применённые теги уровня этого конкретного транспорта.

- Multi-select — выберите один или больше
- Searchable
- Это _vehicle-level_ теги, отдельные от _model-level_ тегов унаследованных от выбранной модели
- Поездки на этом транспорте наследуют эти vehicle-level теги при старте (см. [список поездок](../trips/rides.md) — как работает наследование тегов)

## Сайдбар Field Guide

Правая колонка — это **контекстный гайд**, а не дубликат формы:

- **Live-превью** значений которые вы ввели (чтобы проверить перед сохранением)
- **Встроенная подсказка** обновляется при фокусе поля — объясняет смысл, типичные ошибки, дефолты
- **Auto-fields**: текущий label, статус, IoT, модель, счётчик тегов

Используйте как вторые глаза. На широком экране остаётся видимым при скролле формы.

## Save / Back

- **Back** (`←`) — отбрасывает несохранённое и возвращает на предыдущую страницу (список или деталь в случае edit)
- **Save** — валидирует форму и создаёт / обновляет транспорт. Toast подтверждает успех; ошибки полей подсвечиваются под полем красным сообщением

Если валидация падает (нет label, нет status, дубликат label), страница остаётся открытой с обведённым красным полем.

## Create vs Edit — различия

| Аспект                | Create                               | Edit                                                  |
| --------------------- | ------------------------------------ | ----------------------------------------------------- |
| Label                 | Пусто или _Generate_                 | Заполнено текущей меткой                              |
| Status                | Пусто (выбираете)                    | Заполнено текущим статусом                            |
| IoT Device            | Пусто или выбор из непривязанных     | Заполнено; смена отвязывает предыдущее устройство     |
| Vehicle Model         | Пусто                                | Заполнено                                             |
| Tags                  | Пусто                                | Заполнено текущими vehicle-level тегами               |
| После save            | Редирект на деталь нового транспорта | Остаётся на форме / редирект на деталь (зависит)      |
| Запись в Activity-лог | "Vehicle created by _operator name_" | "Vehicle edited by _operator name_" с диффом по полям |

Оба flow пишут в [Activity-лог](vehicle-detail.md#таб-activity) транспорта.

## Типичные сценарии

- **Завести свежую партию** — Generate label → статус _Not Ready_ → привязать IoT → выбрать Model → сохранить. Когда юнит в поле и протестирован, edit → _Available_
- **Заменить сломанную IoT-плату** — edit → unbind / выбрать новый IoT → сохранить → подождать первый heartbeat (Last signal в детали)
- **Переклассифицировать** — сменить Model при миграции единиц между флотами/категориями
- **Добавить временный тег** — edit → Tags → сохранить (например, "Event 2026-05", "Loaner")

## Полезные приёмы

- **Используйте Generate** для меток — сохраняет нумерацию и избегает дубликатов
- **Ставьте Model рано** — тарифы приходят из модели; без модели поездки на этом транспорте будут с model-less ценовыми правилами
- **Не меняйте статус на _Available_ пока физически не проверили IoT** — райдеры смогут разблокировать сразу
- **Смотрите на подсказку Field Guide** при сомнении — встроенная справка обновляется быстрее этой статьи
- **Activity-лог — это страховка** — каждое сохранение записано с именем оператора и timestamp в [детали транспорта](vehicle-detail.md#таб-activity)
